# Spans that legitimately contain a word from never.txt.
#
# Each line is `<reason> :: <span>`. A banned word passes only when the whole
# match falls inside one of these spans, in the same file. Matching is
# case-insensitive and tolerant of line wrapping and either apostrophe, and it
# runs after the masking: fenced blocks, inline code spans and quoted terms
# are already gone, so a policy key, a status value and the honest-posture
# rule's own `never "safe"` need no line here.
#
# The point of the allowlist is that the word ban cannot be satisfied by
# deleting the disclaimer: "safe" is banned, and the sentences that say static
# analysis cannot prove an agent safe are the reason the word appears at all.
# Those sentences are also in protected.txt, so a rewrite cannot quietly drop
# one to clear the ban — the protected half fails first.
#
# Adding a line here is a claim that the span is honest. It is a change worth
# arguing in a PR, not a way past a red check.

# The posture sentences themselves (protected.txt §1). The word "safe" is the
# content of the claim, in README.md, CONTRIBUTING.md, SECURITY.md and
# docs/trust.md.
a protected posture sentence (protected.txt §1) :: cannot prove an agent safe

# The one form of "guarantee" §4.4 keeps, and the trust page heading built on
# it (protected.txt §5). Deleting the heading would delete the section that
# states the limits.
the §4.4 exception: the negation is the claim :: does not guarantee

# SECURITY.md's opening names the reader's question. The word is what a
# consumer is trying to decide, not a verdict the product gives; the same
# document's §4.6 line says static scanning cannot answer it.
the reader's question, not a verdict the product gives :: whether an agent is safe to install

# Mechanism names that happen to be spelled with a banned word. Each names a
