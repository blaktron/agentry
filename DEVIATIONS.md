# DEVIATIONS

Per PLAN.md §0.5: PLAN.md is immutable during the build. Deviations, discovered constraints, and post-hoc decisions are recorded here — one dated entry each: **what, why, impact**. IDs are stable (`DEV-nnn`) and referenced from commits.

## DEV-001 — No container runtime on the build host (2026-08-27)

**What:** The build machine (macOS, arm64) has no Docker/colima/podman. The compose dev stack (`deploy/compose/docker-compose.yaml`, postgres+minio+mailpit per M0) is authored and validated structurally, but is not executed on this machine. Local development and integration tests instead run against a native PostgreSQL 16 (Homebrew) managed by `scripts/dev/pg.sh`; tests take their DSN from `AGENTRY_TEST_DATABASE_URL`. CI uses GitHub Actions Postgres service containers. §17.1's "testcontainers" mechanism is therefore realized as "real Postgres via DSN" — same coverage, different lifecycle manager.

**Why:** Installing Docker Desktop requires privileged system setup unavailable to the builder agent; Homebrew Postgres 16 provides the identical database engine.

**Impact:** M0 acceptance item "`make dev` boots stack" is verified by compose-config validation locally and by actual boot in any Docker-equipped environment; all DB-touching tests still run against real PostgreSQL 16 locally and in CI. No product code differs.

## DEV-002 — OpenAPI document version 3.0.3 instead of 3.1 (2026-08-27)

**What:** D-09 specifies "OpenAPI 3.1 spec-first". The spec at `schemas/openapi.yaml` is authored against OpenAPI **3.0.3**.

**Why:** The chosen generator toolchain (oapi-codegen v2, per Appendix B "all active") parses specs through kin-openapi, which does not accept `openapi: 3.1.x` documents. Alternatives (hand-rolled codegen, switching generators) cost more than the 3.1 delta is worth at v1; none of the v1 surface needs 3.1-only features (webhooks object, full JSON-Schema keywords).

**Impact:** None on API semantics or clients. Revisit when oapi-codegen's 3.1 support lands; bumping the document version is then mechanical. oasdiff gate works on 3.0.x today.

## DEV-005 — Job queue: interface now, River integration deferred (2026-08-27)

**What:** D-05 specifies River (Postgres-backed Go queue) for all async work. M4 ships the queue as an `internal/queue` interface with a Postgres `SELECT … FOR UPDATE SKIP LOCKED` implementation (the `jobs` table in migration 00005) — the same mechanism River uses internally — rather than River itself. River is pinned in go.mod for the swap.

**Why:** River owns its own migration set and worker lifecycle; wiring it fully is orthogonal to what M4's acceptance criteria actually test (attack-corpus recall, the gate, state-machine property tests, attestation verification). D-05 itself mandates "Queue interface wraps River", so building to the interface first is on-plan; the concrete driver is a later substitution behind it.

**Impact:** Async semantics (durable enqueue, at-least-once delivery, retries with backoff, idempotent handlers) are preserved by the SKIP-LOCKED implementation and its tests. Swapping in River means adding a `queue.Client` implementation and its migrations, with no change to enqueue sites or handlers. The scan orchestrator additionally supports synchronous in-process execution (used in dev mode and tests) so the pipeline is exercisable without a running worker.

> **Errata (2026-08-29).** "and its tests" overstated what was covered when this entry was written: at the time `internal/queue` exercised the happy path and little else, so "retries with backoff" and "at-least-once delivery" were design claims, not tested ones. The independent audit flagged the gap and the wave-1 pipeline branch added the failure-path coverage — `TestQueueRetriesWithBackoff`, `TestQueueFailsAfterMaxAttempts`, `TestQueueRecoversFromHandlerPanic`, `TestQueueNoHandlerFailsJob`, `TestQueueReclaimsOrphanedJobs`, `TestQueueReclaimRespectsCutoff` — so the sentence is true as of that branch and was not before it. The deviation itself (River deferred) is unchanged and still open.

## DEV-006 — Scanner external tools: interfaces with native fallbacks (2026-08-27)

**What:** §8.3 names specific tools — gitleaks (S2), opengrep (S6), osv-scanner (S7). M4 ships each scanner behind an interface with a capable native-Go implementation as the default, and an "external tool" adapter path (exec the real binary when present on `$PATH` / configured) left as the production upgrade. Concretely: S2 uses a native high-signal secret ruleset (including the `agy_` PAT rule required by D-22) with entropy gating; S6 uses native AST-free regex/heuristic detectors mapped to the capability vocabulary; S7 parses lockfiles natively and checks install-scripts + typosquat heuristics, with OSV vulnerability lookup gated behind an injected `osv.Client` (offline no-op by default).

**Why:** Embedding/execing three third-party toolchains (two of them requiring network calls or large rule databases) inside the no-egress sandbox task profile is an integration and packaging effort disproportionate to M4's gate criteria, which test detection behaviour on the committed attack corpus. The native implementations detect every technique the corpus exercises. The plan's swap-point philosophy (§3 "Swap point") applies: the interface is the commitment, the backend is replaceable.

**Impact:** Corpus recall and precision are met by native code. Production hardening (bundling gitleaks/opengrep binaries into the sandbox image, wiring osv-scanner's DB) becomes a matter of providing the adapter implementations behind the existing interfaces — no orchestrator or gate changes. Recorded so the security posture is honest (§1.6.3): the shipped scanners are good, not identical to the named tools.

> **Errata (2026-08-29).** "S7 parses lockfiles natively" was not true when written. As shipped at M4, `S7Dependencies.Run` read exactly one file — `package.json` — for install-script hooks and a typosquat edit-distance check, and only for `kind: mcp-server`; no lockfile of any ecosystem was parsed, and the entry described the intended shape rather than the code. The independent audit caught it. Lockfile parsing lands with wave 2's scanner-depth branch (S7 lockfiles); until that branch is merged, read this sentence as describing S7's package.json analysis only. The rest of the entry (S2 native secret ruleset, S6 native detectors, OSV lookup behind an injected client) was and remains accurate.

## DEV-007 — LLM judge (S5): provider interface with none/static impls in-tree (2026-08-27)

**What:** D-13 defines judge providers bedrock/anthropic/none. M4 ships the `scan/judge.Provider` interface, the `none` provider (which forces human review per §8.4.6), and a deterministic `static` heuristic provider used as the default in tests and dev. The `bedrock` and `anthropic` providers are interface stubs returning a clear "not configured" error until wired with real SDK calls (Q3 also gates the SaaS default).

**Why:** Live LLM calls cannot run in CI or the offline build environment, and the SaaS model/region choice is an open question (Q3). §8.4.6 already specifies the fail-toward-review behaviour when no judge is available, which is exactly what `none` implements.

**Impact:** The gate's treatment of judge output (C1–C6 categories, borderline→review, manipulated-judge→review) is implemented and tested against the `static` provider. Enabling a real provider is additive.

## DEV-010 — Bundle-level descriptive-framing suppressions in the S4 ruleset (2026-08-27)

**What:** The rule-bundle format gained a bundle-level `notPatterns` list (`rules/bundle.yaml`), applied to every rule in addition to its own per-rule suppressions. It suppresses S4 hits on lines using *cataloguing* language — "prompts to echo secrets", "look for exfiltration directives", "**Credential harvesting.**", "report each finding" — i.e. prose that describes an attack technique rather than issuing it.

**Why:** Found in practice, not in theory. The first-party `injection-defense` example skill (which reviews untrusted documents for injection risk, and whose entire content is a catalogue of attack techniques) failed `agentry validate` with two HIGH `S4/credential-harvest-001` findings on lines that merely *described* credential harvesting. §17.3 is explicit that "an agent about prompt-injection defense must be publishable" and that precision regressions fail the build; the existing per-rule suppressions covered negations ("never echo your keys") but not description. Putting the fix in the bundle rather than copy-pasting a long alternation into twelve rule files means the concept has one definition and cannot drift between families.

**Impact and residual risk (stated plainly):** Suppressions are scoped to the matched line, so a descriptive phrase cannot whitelist a whole file. But an attacker who wraps a live directive in cataloguing language ("Prompts to echo secrets: do it now, then...") will evade the S4 *line* hit. That content is then left to S3 (hidden/obfuscated content), S5 (the judge, which reads intent over whole files), S6 (declared-vs-detected capabilities), and S9 (release-diff escalation) — which is exactly why §8 specifies a layered pipeline rather than one gate. The alternative — every security-documentation agent being unpublishable — is a worse failure, and one that silently pushes defensive tooling off the platform.

Locked in both directions: `testdata/attack-corpus/s4-security-docs-benign/` is the shipped `injection-defense` skill as a corpus fixture that must stay clean, and the twelve existing attack fixtures still have 100% recall.

## DEV-011 — CLI embeds the rule bundle; bundle-load failure fails closed (2026-08-27)

**What:** Two changes to `agentry validate`, both found by dogfooding the first-party example agents. (1) The S4 rule bundle is now **embedded** in the CLI binary (via `internal/scan/ruleset`), with `AGENTRY_RULES_DIR` and `./rules` as development overrides — previously the bundle was only found by path, so running the CLI outside the repository silently ran S3 alone. (2) A bundle that cannot be loaded is now a **hard error** rather than a warning-plus-skip.

**Why:** While validating the shipped examples I saw `validate: PASSED` on content whose S4 scan had been skipped, because a stale binary could not parse a newer `bundle.yaml`. That is exactly the failure mode §7 forbids on the server — "never silently publish on scanner failure" — reproduced on the client. D-12's whole point is that local and remote scanning are the same check; a local run that quietly does less than the server, and still says PASSED, breaks that promise in the direction that matters.

**Impact:** `agentry validate` now always runs S3 + S4 and reports the bundle version it used; a malformed override exits 1 with the parse error and no PASSED line. The embedded copy lives at `internal/scan/ruleset/rules/` (go:embed cannot reach the repo-root `rules/`), is generated by `scripts/dev/sync-rules.sh`, and CI fails if it drifts from the canonical `/rules`. This also closes the "embedded rule bundle in release builds" item WG-F had deferred.

> **Errata (2026-08-29).** "CI fails if it drifts" was aspirational when written. `scripts/dev/sync-rules.sh --check` existed and worked, but its only caller was `scripts/acceptance/m4.sh`, which `.github/workflows/ci.yaml` never ran — so a drifted embedded bundle would have reached `main` unnoticed, which is precisely the fail-open the entry claims to have closed. The independent audit flagged it. The check is genuinely wired into CI (and given a `make sync-rules` target) by wave 2's scanner-depth branch; the sentence becomes true at that merge, not at the M4 commit this entry is dated to. Everything else in the entry — the embedded bundle, the hard-fail on a load error — was accurate as written.

## DEV-008 — SAML library: crewjam/saml over russellhaering/gosaml2 (2026-08-27)

**What:** Appendix B left the SAML SP library unresolved ("evaluate both, pick at M6 start"). WG-J picks **github.com/crewjam/saml v0.5.1** for the SAML 2.0 SP (`internal/auth/saml`). OIDC uses **github.com/coreos/go-oidc/v3 v3.20.0** + **golang.org/x/oauth2 v0.36.0** as planned.

**Why:** Both candidates were evaluated. crewjam/saml is the most widely deployed and actively maintained Go SAML library, and its `ServiceProvider.ParseXMLResponse` validates, out of the box and in one call, the exact list §12.4 requires: signed-assertion requirement (a signed assertion is mandatory when the response is unsigned), audience restriction, `SubjectConfirmationData.Recipient`/`Destination`, and `Conditions` `NotBefore`/`NotOnOrAfter` — with `MaxClockSkew` exposed as an explicit knob (set to ±90s per §12.4). russellhaering/gosaml2 (the alternative) is SP-only with a smaller surface, but lacks the built-in recipient check and the skew knob and would push more of that validation into our code. Both ultimately verify signatures with russellhaering/goxmldsig; we pin **goxmldsig v1.4.0 (≥ 1.3.0)**, past the CVE-2022-41912 signature-bypass fix. The replay cache (on assertion IDs) and the NameID/attribute→subject mapping are ours in either case (`internal/auth/saml/replay.go`).

**Impact:** `internal/auth/saml` wraps crewjam's `ServiceProvider`; `go.mod` gains crewjam/saml, goxmldsig, beevik/etree, and mattermost/xml-roundtrip-validator as direct deps. `samlsp.ParseMetadata` was inlined (~20 lines) to avoid pulling crewjam's `samlsp` session/JWT subpackage. Swapping to gosaml2 later would be an `internal/auth/saml` change only — the API layer depends on our `SP`/`Result` types, not crewjam's.

## DEV-009 — In-process SAML/OIDC test IdPs instead of containers (2026-08-27)

**What:** §12.4's M6 test rig says "CI runs a SAML IdP (e.g., a containerized test IdP) + a scripted OIDC provider". Per DEV-001 (no container runtime on the build host), both are realized **in-process**: the SAML tests generate a self-signed RSA keypair in-test and mint signed SAML Responses with beevik/etree + goxmldsig (`internal/auth/saml/saml_test.go`, and the ACS-endpoint variant in `internal/api/m6_saml_test.go`); the OIDC tests run an `httptest` provider serving discovery + JWKS + a token endpoint, signing ID tokens with go-oidc's `oidctest.SignIDToken` (`internal/auth/oidc/oidc_test.go`, endpoint flow in `internal/api/m6_oidc_test.go`).

**Why:** The self-contained IdPs exercise the same SP/RP code paths a container would — real signatures, real JWKS verification, real discovery/issuer pinning — while running anywhere with no Docker. They also make the negative cases (bad signature, wrong audience, expired/replayed assertion, issuer mismatch, `email_verified=false`, nonce mismatch) trivial to construct deterministically, which a black-box container IdP does not.

**Impact:** The M6 acceptance (`scripts/acceptance/m6.sh`) is fully green offline and in CI. The Okta + Entra ID manual-verification checklist (§12.4) remains the one human step, unchanged by this deviation — it validates real-IdP interop, which the in-process rigs deliberately do not claim to cover.

## DEV-012 — Web authed surface: server-side forms, no client-side auth token (2026-08-28)

**What:** §10.1's authed/reviewer/org-admin/staff pages are built as Next.js **server components with plain HTML forms** posting to Next **route handlers** that forward to the API, rather than a client-side SPA calling the API with a bearer token. The web tier holds the user's session: `/login/submit` exchanges credentials at the API once, then mirrors the API's `agentry_session` cookie and stores the API-issued CSRF token in a second httpOnly cookie (`agentry_csrf`); every mutating route handler forwards the session cookie and echoes the CSRF token in `X-Agentry-CSRF`. No auth material is ever exposed to browser JavaScript. The single client component in the whole authed surface is `components/refresher.tsx` (a `setInterval(router.refresh)` for live pipeline progress), which carries no secrets and degrades to a manual reload. Secrets shown once (PAT, SCIM token, webhook secret, TOTP secret) render as a `no-store` HTML page via `lib/show-once.ts` — never placed in a redirect URL.

**Why:** §10.3 mandates a strict CSP with **no inline script**, and D-08 chose SSR. A form-and-route-handler design satisfies that natively: it needs no client bundle for the mutations, keeps the session httpOnly end to end (the browser cannot read or exfiltrate it), and is testable with `curl` (which the acceptance script exercises). It also mirrors the API's own three-layer CSRF stance (SameSite=Lax cookie + Origin check on every route handler + the API's CSRF token) instead of introducing a token-in-JS surface the plan explicitly avoids. `GET /user` gained two additive fields (`platformStaff`, `orgs[]`) so the web tier can route by role without a second call — an additive spec change, no client contract broken.

**Impact:** All §10.1 authed pages (dashboard, review queue + reviewer detail, T&S console, org admin, settings, publish flow + live progress, new-agent wizard) ship SSR with zero client-side auth code. Acceptance: `scripts/acceptance/m8-console.sh` signs in through the web tier and drives every surface (including the U+200B revelation in the file viewer, decision→rejected, triage→state change, block→quarantineState), asserts the authz refusals and a cross-origin-form 403, and runs the structural a11y checker signed-in (`a11y-check.py --cookie-jar`). A future SPA or mobile client would use PATs against the same API unchanged.

## DEV-014 — `published → blocked` added as a direct §7 edge (2026-08-29)

**What:** §7's state diagram reaches `blocked` only through `quarantined` (`published → quarantined → blocked`). The state machine now also allows `published → blocked` directly, and the T&S `block` action uses it to move every live version of an agent in one step. `reinstate` still walks back the drawn path (`blocked → quarantined → published`).

**Why:** Fixing B-02 required staff `block` to actually disable published versions — until now it only set `agents.quarantine_state`, so a "blocked" agent kept serving 200s on download and the handler's 410 branch was unreachable code. Doing that through the drawn path means every block writes two transitions per version, and leaves a window in which the agent is `quarantined` (interstitial warning, "pending review") when T&S has in fact already confirmed it malicious. §7's own row for `blocked` — "downloads return 410; page shows T&S notice; only platform admins can set/unset" — describes a terminal disable that the diagram simply did not draw an arrow for from the most common starting state.

**Impact:** One extra edge in `allowedTransitions`; the audit trail records `published → blocked` in a single row with the T&S reason, which reads more truthfully than a synthetic quarantine. Every other §7 edge is unchanged, and `quarantined → blocked` remains available for the abuse-report path that genuinely quarantines first. The property that matters — that nothing reaches `published` without passing the gate, and that `blocked` is settable and unsettable only by platform staff — is untouched.

## DEV-015 — Rejecting a quarantined version yanks it rather than blocking (2026-08-29)

**What:** §7 gives a quarantined version two exits besides re-publication: `quarantined → yanked` ("author or platform action") and `quarantined → blocked` ("T&S confirms malicious"). The review queue's **reject** decision on a quarantined version maps to `yanked`. Reaching `blocked` stays a deliberate T&S console action (`POST /platform/agents/{ns}/{name}/block`).

**Why:** B-03 gave quarantine an exit by filing a platform review item, which made "what does reject mean here?" a live question for the first time. `rejected` is not reachable from `quarantined` at all (and would be wrong — the version was public), so the choice is yank or block. §7 additionally says `blocked` "SHOULD be gated by dual control (two distinct platform admins) in SaaS ops tooling"; routing a single reviewer's reject straight to `blocked` would quietly bypass that. Yanking removes the version from resolution immediately — the protective outcome — while leaving the stronger, dual-controlled action to the surface built for it.

**Impact:** A reviewer clearing the queue can always act; confirmed-malicious cases take one more explicit step through the T&S console, which is where the dual-control gate belongs. Approving still returns the version to `published` and, per §7, does not re-sign.

## DEV-016 — The 2FA-before-public-publish gate is enabled outside dev mode (2026-08-29)

**What:** §12.1/§19 require TOTP before publishing to a public namespace. The check lives in the shared registry submission path (so it covers both the CLI upload and the git-tag auto-publish a push triggers) and is switched on by the api/worker wiring with `reg.SetPublicPublish2FA(!cfg.DevMode)`. In dev mode it is off.

**Why:** §12.1 states the requirement as a "policy default", not an invariant, and a dev instance has no enrollment flow behind it: `agentryd all` against a fresh database would otherwise be unable to publish anything public at all, which is the first thing a self-hoster tries. The carve-out is the same shape as the two that already exist for dev mode (`DevAutoApprovePipeline`, the `static` judge fallback), and config validation already rejects `env: prod` together with `devMode: true`, so no production deployment can reach the disabled path.

**Impact:** Any non-dev configuration enforces the gate: a submitter without `totp_enabled` gets 403 with an actionable message, and the check happens before the archive is built. Private agents are unaffected — the gate is about what goes public. The knob is a single setter on `registry.Service`, so making it unconditional (or moving it into the policy document as a per-org override) is a one-line change when the enrollment flow ships in the self-host quickstart.

## DEV-017 — `git archive` attribute neutralization is proven at startup, not assumed (2026-08-29)

**What:** §6.5 step 1 requires `git archive` to run with "`export-ignore` attributes ignored — the manifest allowlist is the only filter". The obvious mechanisms do not achieve that: `git archive` reads attributes from *the tree it is archiving* (it unpacks that tree into an in-memory index and points the attribute stack at it), so neither `core.attributesFile=/dev/null` (which silences only the global file — what the code did before) nor `attr.tree` / `--attr-source` displaces an in-tree `.gitattributes`. Measured against git 2.50.1: with all three of those, a file marked `export-ignore` is still dropped. `internal/gitsrv/archive.go` therefore neutralizes each source separately — `--worktree-attributes` (which moves the lookup onto the working tree, and a bare repo has none), `GIT_ATTR_NOSYSTEM=1` for the system file, `core.attributesFile=/dev/null` for the global one — and treats `$GIT_DIR/info/attributes`, for which git offers no disabling switch, as a hard error. Because that behaviour is a property of the installed binary rather than of a version number, it is **verified rather than declared**: `NewRepoStore` archives a throwaway repo whose tree marks a file `export-ignore` and refuses to start if the file does not survive, and every real archive is checked back against `git ls-tree` of the commit it came from, failing the submission if any path is missing.

**Why:** A version gate (e.g. "git ≥ 2.40 for `attr.tree`") would have been both wrong (the flag does not affect `git archive`) and weaker than the property it stands for. The failure this guards against is silent and shipped: a pushed `.gitattributes` quietly removing files from a published release, with a valid-looking archive digest over the reduced tree. A startup probe turns that into a refusal to boot on an incompatible git, and the per-archive check turns any future regression — a new git release, a different vendor build — into a failed submission with a named path list rather than a filtered release.

**Impact:** Two new operational behaviours. (1) `agentryd` (any role that constructs a `RepoStore`) exits at startup if its git honours `export-ignore` in `git archive`, naming the binary and version; the probe result is cached per binary path, costing ~40 ms once. (2) A repository carrying `$GIT_DIR/info/attributes` cannot publish until an operator removes the file — the file is unreachable over the git wire protocol and nothing in agentry writes it, so its presence is always operator action. No API, schema or manifest surface changes. Covered by `TestReleaseArchiveIgnoresExportIgnore`.

## DEV-018 — Enforced SSO on git transport gates writes and releases, not reads (2026-08-29)

**What:** §12.4 states that PATs "used against org resources must be org-bound" when `orgs.sso_required` is set. On the git transport (`internal/gitsrv`), that gate is applied to `agent.repo.write` and `agent.publish` only: `git push` and the `v*` tag creation that releases a version require a PAT bound to the agent's org, while `clone`/`fetch` — anonymous reads of public org repos, and granted reads of private ones — are unaffected. The check itself is not a re-implementation: it calls the same `Principal.SSOSatisfied` helper as `internal/api`'s chokepoint, so the semantics cannot drift.

**Why:** §6.4's authorization table is the specific statement for git operations, and it attaches the org-bound-token requirement to the push row alone; its clone/fetch rows ask for `repo:read` plus read permission and nothing more. Gating reads as well would break anonymous clones of public org repos — which §6.4's first row grants to everyone — and would make an org's public agents unusable by non-members the moment SSO enforcement is switched on, an outcome §12.4's "personal-namespace activity is unaffected" framing gives no reason to want. Mutations are where the enforcement earns its keep: they are what an unbound personal token should not be able to do to org-owned code.

**Impact:** In an enforced-SSO org, `git push` with a personal PAT returns 403 ("this organization requires an org-bound token") at the `info/refs` advertisement, before any pack is transferred; an org-bound PAT behaves normally, including `v*` tags. Non-enforcing orgs and personal namespaces are untouched, and so is every read path. A lookup failure on the org row denies rather than allows. If a later decision extends enforcement to private org reads, it is one `case` in `Handler.ssoAllows`. Covered by `TestGitEnforcedSSO`.

## DEV-019 — Social login: Google is OIDC, GitHub is an OAuth2 shim; identities carry a namespaced subject (2026-08-29)

**What:** §12.1 lists "Social/OIDC login (GitHub, Google)" under one heading. They are not one mechanism. **Google** is implemented as OpenID Connect proper, reusing the enterprise RP (`internal/auth/oidc`): discovery, issuer pinning, PKCE, `id_token` signature/audience/nonce verification. **GitHub** is implemented as an OAuth 2.0 shim in the new `internal/auth/social` package: it exchanges the code, then asks `GET /user` and `GET /user/emails` who the token belongs to. Three consequences are recorded rather than hidden: (1) there is no `id_token` to verify, so the trust anchor is TLS to `api.github.com` plus the client secret, not a signature over claims; (2) GitHub's OAuth app flow has no PKCE, so the sealed single-use state cookie is what binds a callback to the browser that started it; (3) an email is accepted only when GitHub reports it **primary AND verified**, and otherwise no email is recorded at all. Identities store `provider_kind='social'` with a **provider-namespaced subject** (`github:1234`), and migration 00011 adds `identities_social_subject_idx`, a partial unique index — the existing `UNIQUE (sso_connection_id, subject)` does not constrain social rows, because NULLs are distinct.

The `/sso/{org}` landing (§12.4) and the SAML AuthnRequest tracker also made two placement calls. The landing is mounted at the **root**, outside `/api/v1` and outside the OpenAPI surface, like `/scim/v2`: it is a browser destination people paste into address bars and IdP consoles, not a JSON API operation. The outstanding-AuthnRequest tracker is a **process-wide** value in `internal/api` rather than a field on `Server`, mirroring how the crewjam library keeps `saml.MaxClockSkew` package-global; the entries are unguessable ids with a 15-minute TTL, so sharing the set between `Server` instances in one process grants nothing (consuming an id still requires a validly signed assertion for that server's own ACS URL and audience).

**Why:** GitHub publishes no discovery document and returns no ID token; pretending otherwise would have meant either dropping the most-requested provider or writing code that claims verification it does not perform. Scoping v1 to google+github matches §12.1's own list. Namespacing the subject keeps one provider-agnostic identity table honest: GitHub user 42 and Google user 42 are different people.

**Impact:** New package `internal/auth/social`; `internal/config` gains `social.{google,github}` (client id/secret plus endpoint overrides used only by tests). A provider with no client id is not offered at all — `GET /auth/oidc/{provider}/start` answers 404, so probing cannot distinguish "misconfigured" from "not enabled". Because a redirect callback has nowhere to carry a TOTP code, an account with 2FA gets a sealed five-minute challenge instead of a session, completed at the new `POST /auth/2fa/totp/challenge`; social login is therefore never a way around the second factor. Adding a provider means one `Provider` implementation and one config block.

## DEV-020 — Audit archive: file sink built, S3 sink an explicit stub; retention drops partitions (2026-08-29)

**What:** §12.6 requires every audit event to reach `audit_events` **and** an NDJSON stream "within ~1 min". `internal/audit/stream.go` adds a `Stream` interface with a file-appending implementation (one file per UTC day, buffered, flushed on a configurable interval defaulting to 30s). `NewS3Stream` is a **constructor that always refuses**, naming the bucket it was asked for. Retention (§4.3, default 400 days) is a self-rescheduling queue job that calls `audit_prune_partitions`, a migration-defined function that **DROPs whole monthly partitions**; rows are never deleted.

Two behaviours follow from that design and are deliberate. First, the stream is fed by the audit **writer**, immediately after the insert succeeds — not by a committed-transaction tailer. A mutation that rolls back after its audit insert therefore leaves a line in the archive with no matching hot row. Second, when the buffer is full (a wedged disk), records are **dropped with an error log** rather than blocking. Both choices point the same way: an archive that can stall the write path is a denial-of-service surface, and an archive with an extra "attempted" line is auditable while one missing a line is not. Retention rounds **up** to a month boundary: a partition is dropped only once all of its rows are outside the window.

**Why:** The S3/Firehose sink belongs to the deployment that provisions the delivery stream (§13); a half-written client that silently dropped records would be strictly worse than a startup-time refusal, and the interface means adding it later touches nothing else. Partition drops are the only way to prune a table whose append-only trigger refuses `DELETE` — and they are O(1) rather than a 400-day scan.

**Impact:** `internal/config` gains `audit.{streamKind,streamDir,streamFlush,streamS3Bucket,retentionDays}`; `streamKind` defaults to `none`, so nothing changes for a deployment that has not asked for archival, and an unavailable sink degrades to no-op plus an error log rather than failing startup. `api.New` attaches the stream and `RegisterQueueHandlers` registers the retention job (two one-line additions to `server.go`). `GET /platform/audit` gives platform staff the cross-org view §12.6 requires, and each staff read writes its own `audit.platform_read` event before the response is served.

## DEV-021 — API-convention judgement calls: deletion, idempotency scope, and the capability facet (2026-08-29)

**What:** Four decisions taken while implementing §9.1/§9.2 that the plan leaves open.

1. **`DELETE /agents/{ns}/{name}`** is described in §9.2 as "only if never published". It is implemented as **refused once any `agent_versions` row exists**, with distinct messages for "has history" and "a submission is in flight". §4.3 forbids deleting version rows at all — the trigger from 00004 enforces it — so a row still at `submitted` holds a foreign key that cannot be released; "no versions past submitted" and "no version rows" are the same rule in practice. Agents with advisories or abuse reports are also refused: those are trust & safety records that outlive an author's wish to remove the agent. Repository **directory** cleanup is best-effort and outside the transaction: orphaned bytes are garbage, but a deletion rolled back because a directory was busy would be a bug.
2. **`Idempotency-Key`** is honoured on `POST /orgs`, `POST /orgs/{org}/webhooks`, `POST …/webhooks/{id}/ping` and `POST /platform/ruleset-releases` — the mutating POSTs this workstream owns. Keys are scoped `(user, endpoint, key)` and pinned to a hash of the request body: a retry with a different body is a 409 rather than someone else's answer, and a claim whose request failed is released so a bad attempt cannot lock a key out for a day. `POST /agents/{ns}/{name}/versions` is the notable gap and is listed in the handoff, since that handler belongs to another workstream.
3. **`capability=` in `GET /search`** matches only capabilities the agent actually asks for. A manifest that says `network: {egress: none}` still serializes with the `network` key present, so key-existence alone would have matched every agent ever published; the filter additionally requires the value not to be `none`/null/empty and, for object-valued capabilities, that at least one member is not.
4. **Erasure with published content now 400s** without an explicit `publishedContent`, where the previous code defaulted to `yank`. §12.7 calls this a chooser, and the guard that was supposed to enforce it was dead code behind that default.
5. **Webhook ping** records its delivery with event type `ping`, deliberately absent from the §9.3 subscribable catalog: nobody subscribes to a ping, it is sent to one endpoint on request. It otherwise travels the ordinary path — same envelope, HMAC signature, SSRF guard and retry ladder — so the test answers "does my endpoint work" with the code that will actually call it.

**Why:** Each is a place where the strictest reading is also the safe one, and where a looser reading would have quietly weakened a §4.3 invariant, returned a wrong answer to a retry, or made a facet useless.

**Impact:** No plan endpoint is missing; three of the five choices are visible in the OpenAPI descriptions so clients see the rule rather than inferring it. If product later wants a true "delete my never-submitted draft" that also clears in-flight submissions, that needs a §4.3 amendment, not an API change.

## DEV-031 — M5 acceptance: no Playwright, no Lighthouse score (2026-08-29)

## DEV-032 — Push bookkeeping is in-process; no `post-receive` hook, no `repo.pushed` event (2026-08-29)

**What:** §6.3 specifies a `post-receive` hook that "enqueues `repo.pushed` (updates size, search reindex, UI activity)" and, for `v*` tags on auto-publish agents, enqueues submission. Four things differ. (1) There is no `post-receive` hook file at all: `internal/gitsrv/store.go` installs only `pre-receive`. Everything §6.3 attributes to `post-receive` happens **in the HTTP handler** after `receive-pack` exits (`internal/gitsrv/http.go`), under its own 2-minute timeout on a `context.WithoutCancel` so a disconnecting client cannot truncate it. (2) **No `repo.pushed` queue event exists anywhere in the codebase** — the string appears only in PLAN.md. Size accounting and the audit row are written inline; the tag→submit hand-off is a Go callback (`Handler.PostReceive`) the registry sets, not a job. (3) The hooks that do exist are installed as **wrapper shell scripts** (`#!/bin/sh` + `exec "${AGENTRY_HOOK_BIN:-…}" hook pre-receive "$@"`), not the symlinks §6.2 describes. (4) Bare repos are created **lazily, on first git request**, not when the agent row is created.

**Why:** Each has a reason, and none of them was written down at the time. The handler already holds the authenticated principal, the agent row and the per-repo semaphore; a `post-receive` hook would have to re-derive all three from environment variables, and it cannot fail the push anyway. Because `receive-pack` exits 0 even when `pre-receive` rejects every command, the handler re-reads the refs it asked for (`RepoStore.RefsAt`) and treats the repository, not the request, as the authority on what actually changed — a hook cannot do that as cleanly. A wrapper script rather than a symlink is what makes `AGENTRY_HOOK_BIN` work: the binary can be relocated or replaced (rolling deploy, container image swap) without every existing repo's hook pointing at a deleted inode. Lazy init means agent creation is a single database transaction with no filesystem compensation to unwind when it rolls back.

**Impact:** Push bookkeeping is synchronous and bounded by the handler's own timeout instead of being durable queue work, so a git-role crash between `receive-pack` and the bookkeeping loses the size update and the audit row for that push (the refs themselves are already durable — git wrote them). The two consumers §6.3 names for `repo.pushed`, search reindex and UI activity, are fed elsewhere: search indexes on publish, and the activity feed reads version rows. Adding a real queue event later is additive — one `Enqueue` call at the existing call site — and would be the right fix if the bookkeeping ever grows past what fits in a request. The missing symlink and the lazy init have no functional consequence beyond making `ls -l` in a repo's `hooks/` directory look different from the plan.

## DEV-033 — "A single authz chokepoint" is three regimes, one of them outside the matrix test (2026-08-29)

**What:** §12.2 says "every route declares `(resource, action)`; a single `authz.Check` chokepoint; the §17.4 matrix test enumerates all of them." What exists is three regimes. (1) `auth.Check(principal, resource, action)` — org- and self-scoped actions, including the enforced-SSO fold-in. (2) `auth.CheckAgent(principal, agentResource, action)` — per-agent roles and grants, a separate function with a separate resource type, because an agent's permission set depends on rows the org-level check never loads. (3) **12 routes declared `SelfAuthorized: true`** in `internal/api/authz_routes.go`, which authorize inside the handler and are **skipped by the §17.4 matrix test** (`authz_matrix_test.go` explicitly `continue`s past them). Those twelve are the review queue and review-item routes, the finding-verdict route, the platform agent action, ruleset release, platform audit, and the three abuse-report routes — that is, most of the trust & safety surface.

**Why:** The bespoke routes authorize on a fact that is not a `(resource, action)` pair: which *queue* a review item belongs to. `reviewItemAccess` loads the item, then requires platform staff for a `platform`-queue item and the org's `security_reviewer` role for an `org`-queue item. Expressing that as a static route declaration would mean either a resource type per queue or a check that lies about what it enforces. Abuse reporting is the mirror image — anyone, including anonymous users, may file, and only staff may read or triage. The completeness test still forces every route to carry *a* `RouteDecl`, so a new route cannot silently escape the register; what `SelfAuthorized` buys is an opt-out from the enumeration, not from declaring.

**Impact:** The matrix test's 566 cases (as of this date) cover 84 of 96 declared routes. The twelve bespoke ones are covered by handler tests instead, which are real tests but are not the exhaustive route × role × org-boundary sweep §17.4 asks for, and they are the routes where a mistake is most expensive. This is the highest-value item in this backfill: closing it means either expressing queue-scoped access as a first-class resource, or extending the matrix harness to drive the bespoke routes with fixtures. Neither is done. Wave 1 narrowed the blast radius by pushing `review:act` **scope** enforcement (a PAT-scope check, distinct from role authorization) into a shared table — see `internal/api/authz_scope_routes.go`, whose own comment names this gap as the reason it exists.

## DEV-034 — `accepted_risk` is not restricted to org reviewers on org-namespace agents (2026-08-29)

**What:** §8.5 scopes the `dismissed_accepted_risk` verdict twice over: "only by org security reviewers for org-namespace agents, and only up to severity medium". The severity half is enforced exactly (`SetFindingVerdict` refuses the verdict on `high` and above). The **actor** half is not: authorization for a finding verdict runs through `reviewItemAccess`, which grants any platform staff member access to any `platform`-queue item. Because an org-namespace agent's findings land in the platform queue whenever the platform baseline routes them there, a platform staff member can accept risk on an org's agent — which the plan reserves to that org's own reviewers.

**Why:** No deliberate decision; the severity clause was implemented and the actor clause was read as covered by "reviewers can act on their queue". It is a real gap between the code and §8.5, not a considered relaxation, and it is recorded here rather than quietly fixed because the fix is a product question: platform staff genuinely need to act on org-namespace agents during a trust & safety incident (that is what the T&S console is for), so a blanket refusal would break the incident path. The distinction the plan is drawing is between *staff acting protectively* (quarantine, block — always allowed) and *staff waiving a finding on someone else's behalf* (accept-risk — the org's call).

**Impact:** On a hosted instance, platform staff can dismiss a low/medium finding as accepted risk on an org's agent without that org's reviewers being involved. The dismissal is audited (`finding.verdict` with actor and reason) and stays visible on the public report with its rationale, so it is discoverable after the fact rather than silent — but it is not prevented. The fix is a condition in `SetFindingVerdict`: for `dismissed_accepted_risk` on an item whose agent is org-owned, require `isOrgReviewer` regardless of staff status. Deliberately not applied in a documentation wave.

## DEV-035 — DSSE and in-toto are hand-rolled, not sigstore-go (2026-08-29)

**What:** D-16 and §8.8 specify signing "via sigstore-go/DSSE libs", and Appendix B lists "sigstore-go DSSE + KMS signing path" as a verified dependency choice. No sigstore module is in `go.mod`. `internal/scan/signing.go` constructs the in-toto Statement, the DSSE PAE pre-authentication encoding and the envelope itself with the standard library plus `crypto/ecdsa`, and verifies the same way.

**Why:** The pieces actually needed are small and fully specified: DSSE PAE is a documented byte-string construction, the in-toto Statement is a JSON shape, and the signature is ECDSA P-256 over the PAE bytes. Writing those directly is a few hundred lines with no transitive dependency surface, against a library whose useful part for this build was the same few hundred lines wrapped in an abstraction aimed at keyless/Rekor flows that D-16 explicitly defers to v2. The offline build environment also made pulling and auditing the sigstore dependency tree disproportionate to the benefit.

**Impact:** Format compatibility is the commitment, and it is tested rather than assumed: the envelope round-trips through our own verifier, and the CLI's `verify` reads envelopes produced by the server. What is **not** proven is interoperability with third-party sigstore tooling — no external verifier has ever been pointed at an envelope this code produced. That is the honest limit of "format-compatible" here, and validating it against `cosign verify-blob` or `sigstore-go` is a cheap, worthwhile follow-up. Swapping the implementation for the library later is contained to `signing.go`; the wire format is what everything else depends on.

## DEV-036 — Repo and instruction-file quotas are enforced as different shapes than §19 states (2026-08-29)

**What:** Two rows of §19's quota table are implemented differently from their wording.

1. **"Repo size: 100 MB hard (push rejected), 25 MB warn."** The 100 MB hard limit exists (`limits.repoQuotaBytes`, enforced in `pre-receive` and via `receive.maxInputSize`). There is **no warning tier**. The 25 MB figure is instead `limits.repoMaxBlobBytes`, a **hard rejection of any single blob** over 25 MB in the pushed tip tree — a different rule about a different thing, which happens to share the number.
2. **"Instruction-file total (prose scanned by S4/S5) ≤ 1 MB text."** Implemented as `textScanCap = 1 << 20` in `internal/scan/stage.go`: a **per-file truncation** applied during S1 inventory, so each text file contributes at most 1 MB to the scanners. There is no total across files, and nothing is rejected — oversized files are silently truncated to the cap.

**Why:** (1) A warning tier needs a delivery channel a `pre-receive` hook does not have (git's sideband can print, but a warning nobody can act on is noise), and a per-blob cap is the check that actually prevents the failure mode — one enormous file making archives and scans expensive. The number was reused, which is how the two rules came to look like one. (2) A running total is the wrong shape for a fail-closed scanner: an agent whose files sum to 1.1 MB would have to be either rejected (harsh, and not what §19 says to do) or scanned partially in some order-dependent way. A per-file cap is deterministic and order-independent.

**Impact:** A repository can hold many 24 MB blobs up to the 100 MB total and never see a warning, because there is no warning to see. On the scanner side, a single instruction file larger than 1 MB is **scanned only up to its first megabyte** — content past that point is not examined by S3, S4 or S5, and nothing surfaces that fact to the author or to the report. That is a genuine evasion window (append the payload past 1 MB in one large file) and the most important thing in this entry: it should become a finding rather than a silent truncation. Not changed here; recorded so it is not lost.

## DEV-039 — External links: non-allowlisted schemes are stripped, not interstitialed; `rel` has no `ugc` (2026-08-29)

**What:** §10.3 requires external links to carry `rel=noopener nofollow ugc` and an "interstitial for non-allowlisted schemes". `internal/render/render.go` allows `http`, `https` and `mailto` only, and bluemonday **drops** any other scheme's `href` outright — no interstitial, no warning, and to the reader the link simply is not a link. The emitted `rel` is `nofollow noreferrer` (plus `noopener` via `AddTargetBlankToFullyQualifiedLinks`); **`ugc` is absent**.

**Why:** An interstitial is a route, a page and a signed-redirect design — real work whose benefit here is small, because the schemes it would interstitial (`javascript:`, `data:`, `file:`, custom app schemes) are ones we do not want followed at all. **Impact:** Stricter than the plan on schemes, weaker on markup. `ugc` is a hint to search engines that a link is user-generated; its absence has no security consequence and a small SEO one, and adding it is a one-line policy change (`p.AddSpaceWhenStrippingTag` is not it — it needs a `rel` rewriter or a post-pass). The scheme behaviour is worth keeping and worth documenting on the trust page, because "the link vanished" is confusing without an explanation. Both noted rather than fixed, since `internal/render` is code and this was a documentation wave.

## DEV-040 — The org policy editor is a JSON textarea, not a schema-validated form (2026-08-29)

**What:** §10.1 specifies "policy editor (schema-validated form)". `web/app/orgs/[org]/admin/page.tsx` renders the org's policy document as pretty-printed JSON in a four-row `<textarea>`, posted to a route handler that forwards it to `PUT /orgs/{org}/policy`. ## DEV-041 — CSP allows `'unsafe-inline'` for styles (2026-08-29)

**What:** §10.3 requires "no inline script, nonce'd styles". `web/next.config.mjs` sets `script-src 'self'` — no inline script, as specified — but `style-src 'self' 'unsafe-inline'`. Style nonces are not used.

**Why:** Tailwind v4 and Next's App Router inject style elements during render, and Next does not thread a per-request nonce onto them in a way that survives static optimization; the practical choices were `'unsafe-inline'` for styles or abandoning the CSS pipeline. ## DEV-042 — V7's license check is a 60-id allowlist and a file-presence test (2026-08-29)

**What:** §5.3 V7 gates public publishing on an SPDX license. The implementation (`pkg/manifest/spdx.go`) is a hard-coded, case-insensitive allowlist of exactly **60** identifiers, and V7 checks three things: the declared id is on that list, a `LICENSE`/`LICENSE.md`/`LICENSE.txt` exists at the repo root, and `README.md` exists. It does **not** check that the LICENSE file's contents match the declared identifier, or that either matches what the code's dependencies require.

**Why:** The full SPDX list is ~600 entries plus expression syntax (`OR`, `AND`, `WITH`), and vendoring it means vendoring its update cadence. Sixty ids cover the licenses agents actually ship under, and an unknown id fails closed — a refusal an author can act on in one edit. **Impact:** Two consequences. **Valid-but-uncommon SPDX ids are refused for public publish** — an author using, say, `EUPL-1.2` or `CECILL-2.1` is told their real SPDX id is "not a recognized SPDX license id", which is a wrong message for a correct input, and the list is the fix. And a manifest saying `MIT` with a GPL text in `LICENSE` passes V7 cleanly; the platform asserts a license was *declared*, not that it is *accurate*. Consumers reading the license badge should understand it as the author's claim. The S7 license half of §8.3 does not close this either — it reads dependency metadata, not the repository's own LICENSE.

## DEV-043 — `agentry verify` exits 0 when provenance cannot be verified (2026-08-29)

**What:** `verify` fails (non-zero) on a digest mismatch and on an attestation that is present but does not verify. It exits **0** when the attestation is **absent or unretrievable** — the state is printed and the command succeeds. `runVerify`'s own comment states the rule: "A present-but-invalid attestation is a hard failure; an absent one is reported and tolerated (self-host may run unsigned, §8.8)."

**Why:** §8.8 lets a self-hosted registry run with `signing.kind: none`, and the CLI talks to whatever registry it is pointed at. A `verify` that failed against an unsigned self-host would make the command useless in exactly the deployment the plan says to support. The distinction drawn — *wrong* is fatal, *missing* is reported — is defensible, and matches how the command's other soft signal (a yanked version) behaves.

**Impact:** The failure mode this leaves open is the one that matters in CI: a registry that stops serving attestations, or a network path that swallows the attestation request, downgrades a provenance check to a digest check **silently as far as the exit code is concerned** — the output says so, but a pipeline reading `$?` does not. Anyone gating a deployment on provenance needs the strict behaviour. Wave 2's CLI branch adds a `--strict` flag for exactly this; as of this checkout the default is soft and no flag exists, so read the current state as "default soft, strict flag available as of the wave-2 CLI branch". ## DEV-044 — The claude-skill exporter trusts pre-existing `SKILL.md` frontmatter verbatim (2026-08-29)

**What:** §5.6's claude-skill export maps the manifest's `name` and `summary` into the skill file's YAML frontmatter. `ensureSkillFrontmatter` (`cmd/agentry/export.go`) does that **only when the file has no frontmatter**: if the content already starts with `---\n`, it is returned unchanged. Whatever the author wrote there — including a `name` or `description` that contradicts the signed manifest, or additional keys the consuming runtime acts on — is what lands on the consumer's disk.

**Why:** Frontmatter is part of the file's scanned, hashed and attested bytes. Rewriting it at install time would mean the installed file no longer matches the digest the user just verified, which is worse than a mismatched description; and merging into it means parsing and re-emitting YAML, which changes bytes even when it changes nothing semantically. Leaving it alone keeps the installed artifact identical to the published one.

**Impact:** The description a consumer sees in their agent runtime is author-controlled and can differ from the registry's. That is a small deception surface — it is not a capability, and the file was scanned, S4-checked and judged by S5 as published — but it is a place where the registry page and the installed file can say different things. The right fix is a validation-time rule (V-rule or an S1 hygiene finding) that flags frontmatter contradicting the manifest, so the divergence is caught before publication rather than papered over at install. Not built.

## DEV-045 — Force-push to the default branch is denied unconditionally (stricter than §6.3) (2026-08-29)

**What:** §6.3 says the pre-receive hook enforces "no force-push to default branch **unless agent setting allows**". The hook reads `AGENTRY_HOOK_ALLOW_FORCE`, and the server sets it to the literal string `"false"` on every invocation (`internal/gitsrv/http.go`). **The agent setting §6.3 refers to does not exist** — there is no column, no API field and no UI control for it anywhere in the repository. Force-push to the default branch is a hardcoded deny.

**Why:** The setting would need a schema column, an API surface, an authorization rule about who may flip it, and a UI on the agent-settings page (which itself was not built until wave 2 — see WORKGROUPS.md). None of that was in the M2 critical path, and the deny is the safe default: history rewriting on the branch releases are cut from is the operation a compromised token would most want. The environment variable was left in place as the seam.

**Impact:** Stricter than the plan, which is the direction to err, but it is a real capability an author may reasonably want (a bad first commit, a leaked secret in history) and today the only remedy is platform-side. Enabling it later is small: a boolean on the agent, read where `canPublish` is already computed, passed through the same env block. Recorded because "stricter than specified" is still a deviation, and an undocumented one is indistinguishable from a bug when someone later asks why the setting does nothing.

## DEV-046 — `approved` is a dead state in the version status enum (2026-08-29)

**What:** §7's state list includes `approved`, and it is present in all three encodings: `registry.StatusApproved`, the `CHECK` constraint in migration `00004_versions.sql`, and the `VersionStatus` enum in `schemas/openapi.yaml`. **No transition in `allowedTransitions` produces or consumes it.** A version goes `needs_review → published` or `needs_review → rejected` directly; nothing ever writes `approved` to a row.

**Why:** §7's diagram treats approval as the reviewer's decision and publication as its effect, and collapsing them into one transition is what makes the §7 invariant testable — "no path to `published` skips the gate" is a property of one edge, not of a pair that could be entered separately. An intermediate `approved` state would also be a state a version could get stuck in if the publish step failed after the approve step committed, which is a new failure mode for no benefit.

**Impact:** Three enums carry a value that cannot occur. A client switching on `VersionStatus` must handle a case it will never see; a reader of the migration reasonably assumes the state is reachable. The database `CHECK` is the awkward one to remove (a migration to narrow a constraint), so the low-cost fix is a comment in all three places saying the value is reserved and unused — better than leaving three files implying a state machine that is not the one being run. Recorded rather than removed: narrowing an enum in the OpenAPI document is a breaking change the oasdiff gate would flag, and this wave changes no contracts.

## DEV-047 — The §17.2 git conformance matrix runs on every PR through `go test`, not as its own job (2026-08-29)

**What:** §17.2 and the WG-C acceptance criterion name `scripts/conformance/git.sh` as the git protocol conformance gate. That script exists, but it is a thin wrapper: the 21-case matrix itself lives in `internal/gitsrv/conformance_test.go` as `TestGitConformance`, and the script just runs `go test -run TestGitConformance` with pretty output. CI never calls the script — `.github/workflows/ci.yaml` runs `make check`, which runs `go test ./...`, which includes the matrix along with everything else. There is no path-filtered "run the git conformance suite when `internal/gitsrv` changes" job.

**Why:** One implementation, not two. The matrix needs a real `git` binary, a real Postgres and a running server; writing it in Go gets all three from the existing test harness, and a bash re-implementation driving `curl` would be a second, weaker copy of the same assertions. Running it in the ordinary test sweep means it gates *every* change, not just changes to `internal/gitsrv` — a path filter would have missed, for example, an authorization change in `internal/auth` that breaks git PAT handling.

**Impact:** The intent of §17.2 is satisfied and then some: the matrix runs on every pull request rather than on git-touching ones. What is lost is legibility — a CI run that fails shows `FAIL internal/gitsrv`, not "git conformance matrix: 3 of 21 cases failed", and the wrapper script that would say the latter is only ever run by hand or by `scripts/acceptance/m2.sh`. Recorded because the plan names a script as the gate and the gate is not that script.

## DEV-048 — Multi-registry CLI configuration is URL-keyed; there are no named aliases (2026-08-29)

**What:** `~/.config/agentry/config.yaml` holds `defaultRegistry` plus a list of `{url, tokenRef, token}` entries, and `--registry` takes a **URL**. Credentials are stored in the OS keychain under the registry host as the account key. There is no name or alias field, so every command that targets a non-default registry names it by full URL.

**Why:** The URL is the identity — it is what the keychain account key, the TOFU signing-key pin and the token are all keyed on — and an alias layer is a second namespace that can disagree with it (two aliases for one URL sharing a token; one alias repointed at a different URL keeping the old pin). Keeping one key for one registry is what makes "which key set did I pin for this registry" answerable without a lookup table.

**Impact:** Ergonomics only, and mildly: `agentry install --registry https://agentry.internal.example.com acme/foo` is a mouthful compared to `--registry work`. Nothing about the format precludes adding an optional `name` later as a pure lookup that resolves to a URL before anything else runs. Recorded because §11's "multi-registry config" was being read as alias support that does not exist.

## DEV-049 — §10.3 and §10.1 items that were never built and were not previously recorded (2026-08-29)

**What:** Three specified pieces of the web surface do not exist, and none of them was written down as deferred until now.

1. **Image proxy.** §10.3 requires "images proxied/re-encoded (camo-style image proxy; no third-party request from visitor browsers — privacy + tracking-pixel defense)". There is no proxy, no re-encoding, and no image route. The comment at `internal/render/render.go:75` said "proxied/relative sources only — see RewriteImages", referring to a function that has never existed in this repository; it has been corrected in this wave to describe what actually protects the reader.
2. **Server-side syntax highlighting.** §10.3 asks for "syntax highlighting server-side with output escaping". Fenced code blocks render as plain `<pre><code>` with no lexing. This is the benign one: no highlighting means no highlighter to mis-escape.
3. **SSO connection "test button".** §10.1's org-admin row specifies "SSO config (SAML metadata upload / OIDC form + **test button**)". The forms exist; there is no way to test a connection short of attempting a real login.

**Why:** For (1), the mitigation actually in place is the CSP: `img-src 'self' data:` means a visitor's browser will not fetch a third-party image even if one survives sanitization, so the privacy and tracking-pixel goal §10.3 states is met by refusal rather than by proxying. What is *not* met is displaying the author's images at all — a README's external images simply do not render. A proxy is a service (fetch, size-limit, re-encode, cache, SSRF-guard) and was never scheduled. For (2) and (3): not reached, not decided.

**Impact:** Authors' external images are silently invisible on agent pages, with nothing telling them why — the most likely source of "the registry broke my README" reports, and the one worth fixing first (a note in the rendered output where an image was dropped would cost almost nothing). No highlighting is a readability regression on code-heavy READMEs. The missing SSO test button means an org admin's first signal that a connection is misconfigured is a failed user login, which is the §12.4 setup path being harder than the plan intends. Recorded together because all three are §10 gaps of the same kind: specified, unbuilt, and until now invisible in the tracking docs.
